# 凡人问道录 · ImmortalGame

一个纯原生 HTML/JS 的文字修仙放置游戏，从苍梧门杂役一路修到筑基、结丹。无需任何构建工具与依赖，克隆后直接用浏览器打开 `index.html` 即可游玩。

## 特色

- **原著剧情线**：苍梧门 → 玄机子 → 血月试炼 → 青梧谷 → 云京皇宫 → 碎星海
- **数据 / 逻辑 / 表现三层分离**：`data/`（纯数据）+ `js/`（GAME 命名空间模块）+ `index.html`（表现层）
- **修炼系统**：练气十二层 → 筑基 → 结丹；资质、灵根、心境、敛息、青木功层数
- **功法**：青冥剑诀（护盾 + 破甲）、三转归元功（散功重修，永久成长）
- **承露瓶**：绿液催熟灵药（百年/千年）、炼丹（含抗药性机制 1-5 全效 / 6-10 减半 / 11+ 无效）
- **玩法系统**：坊市（含"结丹老怪觊觎"风险值）、黑市轮换、傀儡工坊、灵兽园、妖虫养成、师承红颜羁绊、承露瓶风险泄露
- **副本试炼**：黑石矿洞 / 万妖窟外层 / 魔修弃营（分阶刷装备）、幽冥教赤玉蛛巢穴（两阶段 Boss）
- **多结局**：按筑基期抉择分出 5 种结局（飞升 / 结丹 / 双修 / 独修 / 魔修）
- **地图成长**：境界锁定的地图节点提前展示（可望不可及的期待感），遭遇战按玩家修为匹配怪物池

## 玩法循环

游戏以"半年/月"为单位推进回合，核心循环如下：

1. **洞府经营**：闭关打坐攒修为（半年 +1）、承露瓶绿液催熟灵药（百年/千年灵药、灵木幼苗、玄冰花、龙鳞果）
2. **开炉炼丹**：催熟与采药获得灵药 → 炼制筑基丹/回春丹等丹药；同一丹药越吃越抗药（1-5 颗全效 → 6-10 颗减半 → 11+ 颗无效），逼迫玩家规划长期服药节奏
3. **坊市与黑市**：卖药换灵石，但"药香泄露"与"觊觎风险值"会累积——风险太高，离开坊市时可能被结丹老怪拦路；黑市每 3 个月轮换一次货源
4. **外出历练**：1~3 个月的野外行程，遭遇战怪物按玩家当前修为从怪物池匹配（低修为遇不到金丹怪，反之亦然）；地图上境界不足的节点（如云京城、碎星海）会提前展示但无法进入
5. **副本试炼**：三档分阶副本（黑石矿洞 / 万妖窟外层 / 魔修弃营）刷材料与装备过渡，幽冥教赤玉蛛巢穴为两阶段 Boss 战（先破 4 名血仆削弱 Boss 气场，再面对 30% 狂暴 + 80% 法术抗性的本体）
6. **养成线**：傀儡工坊（矿洞材料造傀儡）、灵兽园、妖虫养成、师承红颜羁绊（李玄尘 / 凌清沅 / 柳蔓儿 / 温巧兮，影响心境与结局走向）

## 剧情脉络

忠于原著早期主线的关键节点链：

```
苍梧门(杂役) → 玄机子收养/夺舍危机 → 玄机世家遗府 → 血月试炼(夺筑基丹)
  → 青梧谷拜师(李玄尘) → 青木功/承露瓶 → 云京皇宫(幽冥教·赤玉蛛)
  → 结丹之争 → 碎星海(当前版本终点)
```

- **练气期**：出身选择（影响初始属性与灵根）、苍梧门到玄机世家的生存线、血月试炼的生死抉择
- **筑基期**：核心玩法全面展开——洞府、炼丹、坊市、副本、羁绊；三种抉择倾向（正道 / 双修 / 入魔）积累因果值
- **结局**（5 种，由筑基期抉择决定）：飞升问道 / 结丹留世 / 道侣双修 / 独修百年 / 堕入魔道

## 运行

直接双击 `index.html`，或：

```bash
cd ImmortalGame
python -m http.server 8080
# 浏览器访问 http://localhost:8080
```

## 测试

基于 Node 的冒烟测试（`vm` 沙盒 + 确定性随机）：

```bash
for f in test/smoke*.js; do node "$f"; done
```

## 结构

```
index.html          入口与界面骨架（脚本按依赖顺序挂载）
css/style.css       样式
data/               纯数据：境界、物品、功法、事件、世界地图、副本
js/                 GAME.* 模块：core / state / combat / map / market / alchemy / ...
test/               smoke 冒烟测试
```

## 关于"去原著化"

本项目早期版本曾参考仙侠题材通俗作品的世界观框架。为降低版权风险，已对全部独创性专有名词（人物、门派、地名、功法、法宝、事件）做**系统性改名**，现版本为**架空原创设定**；仅保留修仙题材通用词汇（练气 / 筑基 / 结丹 / 灵石 / 符宝 / 傀儡 / 心境 等）。

批量改名采用「长词优先」的程序化替换，代码内部 id 与逻辑不动、只改展示文本，共替换 978 处、涉及 47 个文件；替换后全部冒烟测试与基线一致，无新增失败项。
